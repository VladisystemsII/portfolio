SECCIÓN 01
OVERVIEW

RESUMEN
DEL
SISTEMA

VladCRM-COBOL es un sistema de gestión de relaciones con clientes (CRM) cuya lógica de negocio central — registro, actualización, etiquetado, consulta de historial y reportes — está implementada en COBOL bajo formato libre (GnuCOBOL).

En términos de negocio, el sistema centraliza la información de clientes, prospectos, proveedores y contactos prioritarios, junto con el historial de interacciones de cada uno — resolviendo el problema clásico de datos dispersos en hojas de cálculo o agendas sueltas.

El enfoque del proyecto es de COBOL legacy modernization: se conserva la lógica de negocio crítica escrita en COBOL — el lenguaje histórico de los sistemas administrativos empresariales — pero se la conecta con un API Bridge moderno (Python/Flask), una base de datos relacional (MySQL) y un frontend web, demostrando cómo un sistema legacy puede integrarse a una arquitectura actual sin reescribirlo desde cero.

NÚCLEO DE NEGOCIO
7 programas COBOL

Registro, actualización, etiquetado, historial, reportes e importación/exportación de contactos VCF.

CAPA DE INTEGRACIÓN
API Bridge + Web UI

Flask expone cada programa COBOL como endpoint; el frontend web consume la API y MySQL persiste los datos.

SECCIÓN 02
PROBLEM

PROBLEMA
QUE
RESUELVE

Muchas organizaciones — especialmente aquellas con procesos heredados de sistemas administrativos antiguos — enfrentan los mismos síntomas al gestionar su cartera de clientes.

01
CRM disperso

La información de clientes vive repartida entre hojas de cálculo, contactos del celular y notas sueltas, sin un sistema central que la unifique.

02
Procesos manuales

Registrar un cliente nuevo, actualizar su categoría o consultar su historial requiere pasos manuales repetitivos, propensos a errores e inconsistencias.

03
Sin centralización de datos

No existe una única fuente de verdad: clientes, interacciones y etiquetas no están relacionados entre sí ni disponibles para análisis o reportes.

04
Dependencia de sistemas legacy

La lógica crítica del negocio sigue escrita en COBOL, pero sin un puente hacia interfaces modernas que el equipo pueda usar día a día.

SECCIÓN 03
ANALYSIS

PROCESO
DE
ANÁLISIS

COBOL no es un lenguaje nuevo en esta trayectoria. Se aprendió originalmente en la formación universitaria como analista de sistemas, hace más de 30 años. VladCRM-COBOL es la retoma deliberada de ese lenguaje empresarial — actualizado a un entorno moderno de desarrollo, no aprendido desde cero.

El proyecto se diseñó junto con una IA aliada de trabajo ("El Tigre") como mentor técnico de proceso: primero la construcción acelerada del sistema completo, y después una fase deliberada de consolidación — verificar, módulo por módulo, que cada capa (frontend, API, COBOL, base de datos) se comprende a fondo y no solo "funciona". Esa disciplina de no avanzar sin poder explicar el sistema completo es, en sí misma, un ejercicio de análisis.

CRITERIO 01
Retoma, no aprendizaje desde cero

COBOL ya formaba parte de la formación profesional original. El proyecto actualiza ese conocimiento a un stack moderno, en vez de partir de cero en un lenguaje desconocido.

CRITERIO 02
Mapa de herramientas antes de construir

Se trabajó una matriz de herramientas del ecosistema COBOL (núcleo, bases de datos, APIs, contenedores, modernización) clasificada por nivel de dificultad. Sobre esa matriz, el CRM se identificó como el producto ideal para entrelazar las tecnologías de nivel básico/intermedio que sí funcionan bien juntas: GnuCOBOL, MySQL, Flask y una interfaz web.

PRINCIPIO DE FONDO
Construir rápido, después consolidar dominio real

El sistema se construyó primero de forma acelerada, integrando todas sus capas. Después se pasó por un proceso consciente de apropiación técnica: revisar manuales, repasar el código COBOL, y verificar — capa por capa — que el flujo completo (UI → API → COBOL → base de datos) se puede explicar sin necesidad de ver el código. Esa es la diferencia entre ensamblar un sistema y dominarlo.

SECCIÓN 04
SOLUTION

SOLUCIÓN IMPLEMENTADA

Se diseñó una arquitectura COBOL estructurada por módulos independientes, cada uno responsable de una operación del negocio, con lógica batch / procesamiento secuencial sobre archivos CSV — y una integración conceptual con base de datos relacional (MySQL, equivalente a DB2) mediante un esquema normalizado de Clientes, Interacciones y Etiquetas.

01 · ARQUITECTURA
COBOL Estructurado
por Módulos

Cada programa sigue las cuatro divisiones estándar (IDENTIFICATION, ENVIRONMENT, DATA, PROCEDURE) y secciones numeradas (1000, 2000, 3000...) para inicialización, captura, validación y persistencia de datos.

02 · MÓDULOS DE NEGOCIO
Clientes,
Transacciones, Reportes

Registro y actualización de clientes, etiquetado por categoría, registro de interacciones (historial) y generación de reportes filtrados — cada uno como un programa COBOL independiente.

03 · LÓGICA BATCH
Procesamiento
Secuencial sobre CSV

Los programas leen y escriben archivos planos (clientes_nuevos.csv, interacciones.csv, contactos_export.vcf) con organización LINE SEQUENTIAL — el patrón clásico de procesamiento batch en COBOL.

04 · INTEGRACIÓN CON BASE DE DATOS
Esquema Relacional
(MySQL / DB2-like)

Tablas Clientes, Interacciones y Etiquetas con claves foráneas — el equivalente conceptual a un esquema DB2 en mainframe, listo para que los módulos COBOL persistan ahí su salida.

SECCIÓN 05
ARCHITECTURE

ARQUITECTURA DEL SISTEMA

Flujo conceptual de un job en VladCRM-COBOL: el usuario interactúa con la interfaz, una capa de orquestación ejecuta el programa COBOL correspondiente, este procesa o actualiza los datos en la base, y el resultado se devuelve como reporte o respuesta.

01
Usuario
Interfaz web (sidebar + dashboard) o terminal
02
JCL Job / API Bridge
Flask invoca el ejecutable COBOL correspondiente
03
Programa COBOL
Valida, procesa y escribe el resultado en CSV
04
DB2 / MySQL
Persistencia de Clientes, Interacciones, Etiquetas
05
Reportes
Salida CSV / dashboard listo para revisión
SECCIÓN 06
MODULES

MÓDULOS DEL SISTEMA

01 · GESTIÓN DE CLIENTES
Registrar / Actualizar Cliente

Captura y valida nombre, teléfono, correo y categoría (cliente, prospecto, proveedor, inactivo, prioritario), y permite actualizar contactos existentes por teléfono.

REGISTRAR_CLIENTE.cbl · ACTUALIZAR_CLIENTE.cbl
02 · REGISTRO DE TRANSACCIONES
Historial de Interacciones

Consulta el historial de interacciones de un cliente (tipo, nota, fecha, canal) a partir de interacciones.csv, asociado por número de teléfono.

CONSULTAR_HISTORIAL.cbl
03 · REPORTES BATCH
Generador de Reportes

Genera un reporte CSV de clientes filtrado por categoría y/o estado, listo para análisis en Power BI o para alimentar la interfaz web.

GENERAR_REPORTE.cbl
04 · CONTROL ADMINISTRATIVO
Etiquetado de Clientes

Cambia la categoría administrativa de un cliente en el CSV (cliente, prospecto, proveedor, inactivo, prioritario), manteniendo la cartera clasificada.

ETIQUETAR_CLIENTE.cbl
05 · INTERFACE MAINFRAME
Ciclo de Importación / Exportación VCF

Importa contactos desde un archivo VCF (vCard) hacia el CSV de clientes, y exporta clientes_nuevos.csv de vuelta a formato VCF para reincorporarlos al celular.

IMPORTAR_VCF.cbl · EXPORTAR_VCF.cbl
06 · API BRIDGE
Capa de Integración Flask

Expone cada programa COBOL como endpoint REST (/registrar, /actualizar, /consultar, /etiquetar, /reporte, /importar, /exportar) para el frontend web.

app.py · Flask + Flask-CORS

SECCIÓN 08
STACK

STACK TECNOLÓGICO

01 · NÚCLEO
COBOL (GnuCOBOL)

Lenguaje de los 7 programas de negocio: registro, actualización, etiquetado, historial, reportes e importación/exportación VCF.

02 · ORQUESTACIÓN
JCL (conceptual)

Representa el job control que en un mainframe real encadenaría la ejecución de los programas COBOL como batch.

03 · BASE DE DATOS
MySQL (DB2-like)

Esquema relacional con tablas Clientes, Interacciones y Etiquetas — equivalente conceptual a un esquema DB2.

04 · PLATAFORMA
z/OS (conceptual)

El proyecto simula el entorno mainframe z/OS como contexto de ejecución objetivo de los programas COBOL.

05 · API BRIDGE
Python / Flask

app.py expone cada ejecutable COBOL como endpoint REST, con Flask-CORS para conectarlo al frontend web.

06 · FRONTEND
HTML / CSS / JS

Dashboard con sidebar, contactos, historial y ciclo VCF, consumiendo el API Bridge en localhost:5000.

SECCIÓN 11
ROADMAP

PRÓXIMAS
MEJORAS

01 ·

Integración con APIs modernas: exponer los módulos COBOL mediante una API REST documentada (OpenAPI/Swagger) sobre el API Bridge ya existente.

02 ·

Migración parcial a microservicios: encapsular cada módulo COBOL (clientes, historial, reportes, VCF) como un servicio independiente desplegable por separado.

03 ·

Interfaz web de consulta ampliada: dashboard con estadísticas en tiempo real, búsqueda avanzada y edición directa de clientes desde el navegador.

04 ·

Automatización de reportes: jobs programados que generen y envíen reportes periódicos (diarios/semanales) sin intervención manual.

RESULTADO

Un sistema legacy en COBOL conectado a una arquitectura moderna — la base de un proceso real de modernización empresarial.

7 módulos COBOL, 1 API Bridge en Flask, esquema relacional con 3 tablas y un frontend web — demostrando disciplina de sistemas legacy junto con una visión clara de modernización.
